# 全屏卡顿：待确认的下一步

> 历史方案，已执行：用户随后授权由我选择路径，0.2.2 最终采用精确涡旋系数缓存与第一人称自身可见性策略。结果、取舍和验证范围见 [全屏优化记录.md](全屏优化记录.md)。下文保留提出方案时的证据，不表示当前仍等待技术选择。

2026-10-02。当前运行库 0.2.1；用户反馈全屏明显卡顿、窗口轻微卡顿。沿用用户“先确定后执行”的要求，本页为诊断与待选方案，尚未实施第 3/4 步。

## 当前证据

- 此前独立第三人称对照为 1280×720、25 个冻结密度包、resolution=1、steps=128，体积 GPU 中位耗时约 14.7 ms；这不是用户全屏的实测耗时。
- 显示器当前为 2560×1440、170 Hz。若游戏全屏采用原生分辨率，其像素数为上述对照的 4 倍；不能据此直接断言 GPU 耗时或 FPS 恰好按 4 倍变化。
- 最后一次 status.json 更新时间 18:13:49：0.2.1、第一人称、volumeCoverage=1、sceneCopyCoverage=1、24 个密度包、GL error=0、failed=false。查询时无 ASTRA Java 进程或 9876 监听，日志显示已保存退出。因此这份状态是退出前快照，不是实时帧率记录。
- 保存的 options.txt 为 fullscreen=false、enableVsync=true、maxFps=120、renderDistance=12；这些值不能替代全屏时的实时帧缓冲尺寸和呈现测量。
- 当前 auraSample 在每个有效积分端点做 3 次 RK2 回溯，每次调用 2 次 smokeCurl，每次含 8 个局部涡旋贡献，即最多 48 个涡旋贡献，随后还计算噪声、薄层距离与侵蚀。全分辨率射线大量重复这一计算。

现有证据支持 GPU 像素/积分负载是主要排查方向；全屏呈现、VSync 与实际游戏背景负载仍需测量区分。

## 推荐：先试 GPU 流场缓存

把重复的坐标回溯计算转为 GPU 三维缓存，再由射线采样缓存；薄烟的距离与 Gaussian 段积分保持独立，保留输出分辨率、气团数量与运动参数。缓存插值和时间插值属于近似，不能预先承诺逐像素一致，不能以普通屏幕模糊掩盖误差。

先完成独立原型，不提前更新用户运行库。使用 2560×1440 与 1280×720、第一/第三人称、相同配方进行特效关闭/当前实现/候选实现对照，记录实际帧缓冲尺寸和各 pass 异步 GPU 耗时、帧间隔。另检查近距离薄烟清晰度、卷曲形状、连续运动、遮挡、移动残影、资源重载与 GL 状态。

只有收益明确、画质检查通过后才形成新的生产包并实装。若缓存损失细节，应调整缓存精度或保留现有计算，不默认降低整体分辨率或生成率。

## 可选路线

- 自适应采样：按投影尺寸、距离和局部变化减少积分段；收益较快，但可能损失细丝或出现闪烁，须用户接受这项取舍。
- 只补测：先完成实际分辨率和呈现负载的诊断，不改渲染算法。

GPU 缓存的具体更新预算、精度与实现路径在独立原型中确定；本文没有承诺尚未测量的速度或游戏帧率。
