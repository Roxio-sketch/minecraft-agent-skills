# 近景覆盖预算与积分目标池

用于体积积分随屏幕覆盖增大而变重的现有渲染器。先确认GPU瓶颈；CPU微优化或只减少发射器数量不一定改善单个全屏体积场。

## 按覆盖选择精度

按实际相机模式、挂点与屏幕覆盖做决策。第三人称贴身低视角同样可能让体积覆盖全屏，不能只在第一人称分支降预算。

可先保留密度公式、配色、运动及沿射线采样次数，只减少屏幕射线数量。先使用投影包围盒加积分边界得到原生矩形，再选择满足积分像素预算的最大分档尺寸；小覆盖对象保持原生尺寸。预算针对实际scissor像素，不是整张纹理面积或只按相机距离猜测。

设原生尺寸W/H、带边界矩形[x0,y0,x1,y1]、候选积分尺寸Tw/Th：

```text
ix0 = floor(x0 * Tw / W); ix1 = ceil(x1 * Tw / W)
iy0 = floor(y0 * Th / H); iy1 = ceil(y1 * Th / H)
pixels = (ix1 - ix0) * (iy1 - iy0)
```

候选尺寸取整后重新核对pixels，不能只用比例平方近似。积分清理、重建与边界扩张的矩形要与实际绘制一致。设置最低分辨率时说明预算是否仍有保证；每次绘制的预算不等于多人全帧总预算。

可用 `1, sqrt(0.5), 0.5, sqrt(0.125), 0.25, …` 等有限档位，避免连续比例制造大量尺寸。二进制偶数档可直接按指数计算，避免重复浮点乘法将精确0.5变成略大于0.5，多分配一行/列。跨档细节跳变明显时，再按实测考虑迟滞。

## 共享深度与复用颜色目标

不要每个对象切换比例就释放并重建颜色和深度FBO，这会把稳定的像素负载换成分配抖动。

- 原生深度目标按窗口尺寸与深度格式管理，各积分尺寸共享；仍按已有深度复制/遮挡路径使用。
- 颜色FBO按有限分档尺寸懒分配并缓存；同帧身体、武器、远近对象切换只选择现有目标。
- 池键覆盖影响附件兼容性的尺寸、格式或代际；窗口/格式变化、资源重载和退出时清理失效目标。不要让不受约束的连续比例进入永久缓存。
- 记录显存上界。例如每档像素数约减半时，所有档位颜色面积之和小于约两张原生颜色目标；不同模式的独立尺寸另计，不能当作零显存开销。
- 每次复用先清空会被访问的积分区域；深度复制范围还须覆盖低分辨率重建tap在原生空间的足迹，避免跨对象残像和边缘漏样。
- 懒分配失败释放本次创建的附件；纹理上传/分配期间正确隔离并恢复PBO与UNPACK状态。其余GL恢复规则见[深度重建参考](volume-depth-composite.md)。

## 验证容易漏掉的部分

冻结同一视图、时刻、材料、模拟状态和深度，对原生与预算模式交替暖机和GPU计时，同时保存最终图像。验证实际uniform中的步数、积分目标尺寸和像素数，不能只记录配置值。原生参照必须真的使用原生尺寸。

保留两类证据：固定黑色深度场景下的体积加合成GPU计时，以及正常实体/地面深度与外部光影最终合成的实机画面。前者若绕过光影最终管线，应明确注明，即使光影包已装载。独立动态场景的事件耗时可辅助说明，但不替代冻结配对，也不换算成用户整合包FPS。

覆盖用户原始截图尺寸与实际相机姿态；预览工具缩小后的图像尺寸不能当作原始尺寸。检查白/亮、蓝及暗材料的细焰、轮廓、运动、遮挡和资源重载。关闭优化应恢复原生精度，小范围远景验证最终图像保持一致。减少屏幕射线会柔化细丝与焰尖，不能因沿射线公式一致就宣称图像等价。

远景用例要验证投影矩形实际低于预算。脱离主体的粒子或保守包围盒可能让十几米外仍超过预算；此时降档可以正确，不应为了通过“远景原生”断言而破坏预算。

对不同窗口尺寸和随机覆盖矩形检查预算及取整；目标暖机后交替绘制原生/低分辨率、身体/武器对象，确认不再创建颜色/深度目标。分配统计使用累计计数差。资源探针若临时保存并清零静态GL ID，还须隔离整个目标池，防止清理函数删除保存着的真实目标。

## 实测案例及边界

2026-10-16，Forge 1.20.1/Java17、RTX4060Ti，第三人称贴身仰视体积火焰。每次绘制9万积分像素、512步；1903×1439时337×255目标共85,935像素，1920×1440时340×255目标共86,700像素。这些参数是该案例的画质选择，不是通用默认。

1903×1439白火固定配对，体积加合成GPU中位数326.39→11.28ms；同样探针在Solas装载环境326.95→11.17ms，但绕过光影最终管线。采用2轮暖机、7组交替配对；蓝/暗材料也验证。32米小覆盖远景保持原生尺寸，两种窗口的最终RGB差均为0。用户安装后确认优化成功；近景细节仍存在降分辨率取舍。

实际世界1920×1440低视角另测：原版AFTER_PARTICLES事件286.53→11.23ms，Solas259.43→11.46ms；包含其他事件、且前后动态场景并未冻结，不把这些值当作精确配对或游戏FPS。原版/Solas各53场，通过随机覆盖预算、目标暖机切换零新增分配与实机画质检查。
