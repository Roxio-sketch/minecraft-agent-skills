## MCP-HELPER

The bundled `mcp-debug/index.html` documents these HTTP routes:

- `GET /api/status`: version, loader, port, control-mode and availability state.
- `GET /api/calls`: recent request/response records.
- `GET /api/screenshot`: screenshot data.
- `GET /api/events`: server-sent event stream.
- `POST /api/cmd`: JSON body starts with a `cmd` property.
- `GET /debug` and `/`: bundled debug UI/static page.

After the status route responds successfully, the following are read-only probes shown in the debug page's command inventory:

```json
{"cmd":"get_player_info"}
{"cmd":"get_world_info"}
{"cmd":"get_screen_buttons"}
```

Send each as an individual `POST /api/cmd` request with `Content-Type: application/json`. Confirm the returned world name and live values before any write. For command execution, `execute_command` takes a `command` field; use a read-only Minecraft query first, and do not infer that command permission exists just because the UI exposes the selector.

The debug page's command selector includes `get_player_info`, `get_world_info`, `get_screen_buttons`, `execute_command`, `screenshot`, `click`, `press_key`, `type_text`, helper navigation/movement/commands, area scans, and structure operations. Read-only and mutating operations are mixed together; inspect the specific handler before use. Do not treat the debug UI selector as evidence that a command is safe or that the route is currently responsive.

The HTTP handler accepts some methods absent from the debug page selector. On the observed build, these were verified via `POST /api/cmd`:

```json
{"cmd":"enter_control_mode"}
{"cmd":"exit_control_mode"}
{"cmd":"open_to_lan"}
```

`enter_control_mode` returned success and changed `/api/status` to `control_mode: true`; `execute_command` then accepted `{ "cmd":"execute_command", "command":"/say MCP-HELPER programmatic control probe" }`. The response said it sent `connection.sendCommand`; `/api/calls` recorded the request and `logs/latest.log` contained both server and chat echoes. That is verified programmatic world control. Use a harmless command and verify its result. `open_to_lan` exists in the internal dispatch map; probe its response and resulting status/log in the installed version before relying on it.

The Forge bootstrap accepts `--quickPlaySingleplayer ASTRA_VFX_TEST`. A successful test path launched Axolotl, parsed its child arguments in memory, removed the Theseus Java agent/IPC layer, retained the Forge bootstrap arguments, substituted that quick-play argument, and started the game from the instance working directory. ## Photon 1.1.17

The exact source is available publicly: `com.lowdragmc.photon:photon-forge-1.20.1:1.1.17:sources` from the official FirstDark Maven. The official repo's `1.20.1` branch points to commit `507499fbe5a3fc72bb90993e059848cbb31f13ca`, titled `v1.1.17`. The source artifact and the official binary JAR at that Maven coordinate were inspected; the binary's SHA-256 matched the installed Photon JAR. Use this source/release pair as the authority for Photon 1.1.17; do not apply Photon 2.x documentation.

### File format and resource loading

- Editor project files use `FXProject` NBT with root keys `resources`, `fx`, `_version` (currently 1). `saveProject(File)` writes uncompressed NBT.
- Exported runtime `.fx` files are gzip-compressed NBT. Root keys are `fx` and `_version` (1). `fx` contains `mainFX` and `subFXs`; each FXData contains `fxObjects` (a list of compound tags).
- The editor export default folder is `<LDLib editor workspace>/assets/photon/fx`. Runtime resource lookup for `namespace:path` is `assets/<namespace>/fx/<path>.fx` through Minecraft's resource manager. A resource pack can therefore provide a test FX, for example `assets/testnamespace/fx/probe.fx` addressed as `testnamespace:probe`.
- `FXHelper.getFX(ResourceLocation)` parses and caches the runtime asset. `/photon_client clear_client_fx_cache` clears that cache; the source does not wire this command to resource-pack discovery/reload. To make a newly added resource visible, arrange a normal Minecraft resource reload (or restart with the pack enabled), then clear the Photon cache if that FX was already looked up.

### Emitters and API

- `ParticleEmitter` registers as `_type: "particle"`; `TrailEmitter` registers as `_type: "trail"`. Both extend `Emitter`, carry a `config` compound persisted through LDLib auto-persistence, and write `_version: 2`. Particle settings live in `ParticleConfig`; trail settings in `TrailConfig`. `FXData.objects()` is the emitter/game-object list.
- Public client API exists: `FX.deserializeNBT`, `FX.serializeNBT`, `FX.createRuntime([deepCopy])`, `FX.createInternalRuntime`, `FX.createSubFXRuntime`; `FXRuntime.emmit(IEffect)` begins emission and `destroy(force)` tears it down. `IFXEffect` exposes `start()`; built-in `BlockEffect` and `EntityEffect` implement it and use real client levels/entities/blocks. These are in-process client APIs, not a standalone command-line tool or remote HTTP API.
- Built-in server commands play resources: `/photon fx <resource> block <pos> ...` and `/photon fx <resource> entity <entities> ...`; `/photon fx remove block <pos> [force <bool> [location <resource>]]` and corresponding `entity` removal stop bound effects. They require permission level 2 and send packets for client-side resource loading/runtime creation. Normal emitter lifetimes can also end naturally.
- `/photon_editor` only opens the editor; it does not itself create an FX. The editor supports emitter construction and scene preview; export writes the documented NBT resource format. MCP-HELPER's `gui_state`, `client_window`, `gui_pointer`, and click/key controls can drive this GUI programmatically, but they remain UI automation rather than a Photon authoring API.

### Same-ID update and cache invalidation

`photon-test10` adds `{"cmd":"photon_clear_fx_cache"}` to `POST /api/cmd`. It requires MCP control mode, calls Photon 1.1.17's `FXHelper.clearCache()` on the client thread, and returns `{"ok":true,"removed":<count>}`. It clears the client's whole parsed FX cache; it does not stop already-running effects or reload resources. A zero count is valid when nothing was cached. `/photon_client clear_client_fx_cache` is a client command: sending it through the server-side `helper_command` executor was rejected in this setup.

For an already-played single-particle ID, use this order:

1. Remove its existing runtime at the known test target and wait for its particle lifetime to expire. Capture the empty baseline. For the isolated block used here, `helper_command` executed `/photon fx remove block -276 64 -805`; this removes effects at that block, so use a dedicated test position.
2. Call `photon_update_fx` with the same ID and the changed fields. Inspect it with `photon_inspect_fx` to confirm the stored values.
3. Poll `photon_status` until `reload` is `complete` and `selected` is true, with a bounded deadline (45 seconds worked locally). Stop on reload failure or timeout.
4. Call `photon_clear_fx_cache` and require `ok: true`. If the installed build lacks this operation, use a verified local client-command path before claiming a same-ID update works.
5. Return from a pause menu with `client_resume`, replay at the same target, wait for particles to appear, and capture the changed effect. Stop it again and confirm it disappears after decay.

The test10 run used `codexvariant:cache_cycle_20260927` at block `-276 64 -805`, size 0.15, lifetime 60 ticks, speed 1, rate 12, duration 100, looping true, and maxParticles 1000. The same client session first rendered white `#FFFFFFFF`, then stopped, updated to pink `#FFFF40A0`, completed resource reload, cleared one cached entry, and rendered pink on replay. Screenshots are `evidence/test10-cache-white.png`, `evidence/test10-cache-after-stop.png`, `evidence/test10-cache-pink-after-clear.png`, and `evidence/test10-cache-pink-removed.png`. The final image shows no effect after removal and five seconds of decay. The world advanced from night to day between captures; the evidence establishes particle color change and disappearance, not a pixel-identical lighting comparison. The earlier `test9-color-after-update-no-clear.png` stayed white despite pink file readback, demonstrating why resource reload alone was insufficient.
