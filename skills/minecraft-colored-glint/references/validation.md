# 验收与排错

按本次实现范围选择场景。读源码、纹理校验、构建通过、游戏画面通过是四种不同证据；每一层只报告实际完成的内容。

## 配置与静态检查

- 未配置、有效 ID、default、未知 ID、空 stack、错误类型数据都不会破坏原版回退。
- `forceFoil` 与颜色解耦：已附魔且 force=false 仍可彩色；未附魔且 force=false 不多出流光。
- 不在渲染查询中修改 stack；客户端 renderer 不被公共注册/专用服务器加载。
- 核对 Mixin 目标签名、表达式、boolean ordinal、客户端配置及打包 refmap；新增纹理路径和大小写实际存在。
- 追踪每种宣称支持的模型到实际 draw 和 flush；记录未经过 hook 的路径。
- 需要时用项目自带 Gradle wrapper 构建与 reobf。仅检查 Java 文件存在或 JSON 合法不等于构建通过。

## 游戏场景

| 场景 | 应观察的结果 |
|---|---|
| 未附魔且无配置 | 与原版一致，无额外光层 |
| 已附魔且无配置/default | 保留原版对应分支的流光 |
| 已附魔、红色、force=false | 红色流光仍出现 |
| 未附魔、蓝色、force=true | 显示蓝色，无需改变原附魔数据 |
| 同屏红、蓝、紫、绿 + 无配置物品 | 每个物品颜色独立，默认物品无串色 |
| 移除配置/未知 ID | 回退策略正确，不继承上一物品 |
| GUI、第一/第三人称、掉落实体、展示框 | 用户要求覆盖的视角正确，姿态和模型保留 |
| 三维模型、弓拉伸/其他 override | 所需形态正确，侧面和动态部分无固定壳残影 |
| 不透明遮挡、透明基础层 | 无穿墙；透明情形按已支持的分支验收 |
| 连续渲染、嵌套 render 与异常恢复 | 后续物品不继承旧配置，外层颜色恢复 |
| 资源重载，连续至少两次 | 新纹理/shader 生效，无失效引用或重载后串色 |
| 若范围包括穿戴护甲 | 装备各部位和实体路径独立检查 |
| 若范围包括 Cosmic 共存 | 星空仍正常，流光没有被后续 pass 完全覆盖 |

运行验证需记录具体 MC/loader/Java、物品与配置、视角、场景或截图、日志中的 shader/Mixin/GL 错误。截图证明某个时刻的外观；连续录像或分时截图才能证明流动。没有运行环境时保留以上用例为待验收，不填写伪造 pass。

## 症状到原因

| 症状 | 优先检查 |
|---|---|
| 仍是原版紫光 | 真正调用的 helper/RenderType 分支、Mixin 是否命中、ID 与纹理绑定 |
| 只有 force=true 才能变色 | 是否照搬 `processStack` 的 always 条件 |
| GUI 正常，手持或掉落不对 | 是否只覆盖 direct；实体/透明/特殊 helper 是否漏掉 |
| 护甲背包图标有效，穿上无效 | 是否根本没有装备层调用者；不能只看 ARMOR_LAYERS 存在 |
| 前一个物品颜色串到下一个 | 静态 stack 恢复、uniform 写入与 flush 时机、稳定层缓存 |
| 没有流光或出现穿透 | 是否匹配基础深度与几何，draw 顺序、output target、shader 顶点格式 |
| 重复过亮 | 原层和新层是否都画了；自定义 model 是否又落回重复路径 |
| 贴图变成整块亮色 | 混合方式、RGB 强度、UV/纹理矩阵和恢复；不要先改 alpha |
| 重载后失效 | 自定义 shader/uniform/sprite 缓存是否过期；普通纹理地址是否正确 |
| 星空正常却没有附魔光 | 自定义 renderer 是否直接取基础 buffer，Cosmic 是否在后面覆盖 |
| 内存或 draw call 持续增长 | 是否逐帧建 RenderType，或用连续时间/颜色作为无界缓存 key |

## 本技能本身的验证

`quick_validate.py` 检查技能结构；调色脚本的行为测试检查尺寸、alpha、颜色运算、侧车文件、错误输入和覆盖保护。源贴图摘要、Markdown 链接和安装副本一致性可静态核对。这些结果不等价于 Minecraft 模组构建或 GPU 场景通过。

新增 `author_glint.py` 需另外验证：任意 HEX 和非均匀色标、sRGB/线性光中点、HSV 最短路径与无彩端点、repeat 闭合/pingpong 往返、时间周期、空间/时间模式分离、alpha/尺寸、中性 shader 载体、输入保护、无效/动画 metadata、输出资源路径及 uniform 契约。来源项目中 `skill-validation/test_glint_authoring.py` 可重跑；不要要求其他使用者必须拥有该项目路径。

来源项目的 `validate_glint_shaders.py` 通过隐藏 WGL 上下文编译/链接 shader，并在 RGBA32F 目标上比较 GPU/Python 色值，使用本地 1.20.1 `fog.glsl` 解析导入。它不启动游戏，不证明 Minecraft 的 shader 注册、RenderType、混合与资源重载已经接入。没有对应环境时应记为未执行，不能用 JSON 解析冒充 GPU 编译。

## 渐变新增游戏验收

| 场景 | 应观察的结果 |
|---|---|
| 用户指定的新 HEX/色标而非预设 | 实际资源和配方使用用户值，游戏注册 ID 可解析 |
| spatial 与 temporal 对照 | 前者随纹理坐标分色；后者同一时刻整体同色 |
| traveling 的两个时刻 | 色场按配方时间变化，不只证明原版纹理在滚动 |
| 完整周期边界前后 | repeat 没有首尾跳色；pingpong 正常往返 |
| 两把不同渐变 + 原版对照 | 各自保持参数与相位，默认物品不染色 |
| 静态 shader 路线 | 采中性载体，没有对已染色 PNG 重复染色 |
| 暂停/继续与长时间存档 | 符合声明的时钟策略，无明显浮点抖动 |
| 两次资源重载 | 当前 shader/uniform 与新资源对应，不复用旧对象 |
| 声称剑尖/柄端固定配色时 | 不随 glint 纹理滚动迁移；多视角及形态仍对齐 |

离线预览可证明配色样本，不能证明这些游戏场景已通过。报告应分别列出“原九色游戏基线”和“新增渐变验证”，避免继承旧 `runtime_verified=true` 的笼统结论。

来源工程 0.2.0 已有新四套配方的 15 场景实测与 73 项证据检查，见 [运行记录](forge-1.20.1-runtime.md)。用 `colored-glint-lab/scripts/validate_runtime.py` 核对对应跑次；它检查已有证据，不启动游戏。完整周期检查针对实际 draw 时间回绕，不能单独证明每一帧视觉连续；暂停检查针对新增颜色时间，不能要求仍使用原版滚动矩阵的截图完全一致。
